# 프론트 렌더링 계약 + 설계 근거

> **엔드포인트 계약의 정본은 백엔드 [`docs/API_SPEC.md`](https://github.com/2026-AIHwaseong-project/hwaseong-dashboard-backend/blob/main/docs/API_SPEC.md) 입니다.**
> 경로·파라미터·응답 스키마를 찾는다면 그쪽을 보세요. 이 문서에는 규격이 없습니다.

이 문서는 두 가지만 남깁니다.

1. **백엔드가 알 길 없는 프론트 렌더링 의존성** — 서버가 이걸 어기면 오류 없이 화면만 조용히 망가집니다.
2. **설계를 그렇게 정한 이유와, 해봤다가 안 된 기록** — 같은 논의를 다시 하지 않기 위한 것입니다.

원래 이 문서는 백엔드가 없던 시절의 발주서(830줄)였습니다. 서버가 완성되면서 규격부는
`API_SPEC.md` 로 옮겼고, 옮길 수 없는 것만 여기 남겼습니다.

---

## 1. 프론트 렌더링 계약

서버가 지켜야 하는데 API 명세만 봐서는 알 수 없는 것들입니다.
**어기면 예외가 나지 않고 화면이 조용히 틀려집니다.**

### 1.1 등급(`bins`)은 서버가 계산한다

지도 채색과 산점도 점 색은 서버가 준 `cells[].bins` 로만 결정합니다.
프론트는 임계값으로 직접 분류하지 않습니다 — `scale.miThresholds` 는 **범례 눈금 표기에만** 씁니다.

`bins` 가 빠지면 `map.js` 의 `binOf()` 가 `cell.bins || {}` 로 폴백해 mi=3, demand/supply/flow=2 로
전부 같은 등급이 됩니다. **오류 없이 지도가 균일한 색으로 칠해집니다.** 그래서 등급 계산은 서버 책임입니다.

산점도는 가로축 `zSupply` · 세로축 `zDemand`, 점 색은 `bins.mi` 입니다.

### 1.2 정류장 `id` 는 불투명 문자열이다

프론트는 정류장 `id` 를 **파싱하지 않습니다.** `arsNo` 는 프론트 코드 어디에서도 쓰지 않습니다
(grep 0건). 따라서 백엔드가 ID 체계를 바꿔도 프론트 코드 변경은 없습니다.

단, `/stops` 의 `id` · `cells[].nearestStopId` · `/stops/{id}/profile` 의 경로 파라미터
**세 곳이 동시에 같은 형식**이어야 합니다.

### 1.3 `nearestStopId` 는 `/stops` 의 `id` 와 문자열이 정확히 같아야 한다

격자를 클릭하면 이 값으로 정류장을 찾아 선택·포커스합니다.
형식이 한 글자라도 다르면 예외 없이 **아무 정류장도 안 잡힙니다.**

### 1.4 `hours` · `boardings` · `alightings` 는 길이가 같아야 한다

프론트(`drawProfile()`)는 길이를 검사하지 않고 `hours` 인덱스로 곧장 참조합니다.
어긋나면 막대와 표가 **조용히 한 칸씩 밀립니다.** 서버가 보장해야 합니다.

### 1.5 정류장 `kind` 는 지도 마커에만 쓴다

`hub` 면 4.6px 고정 + `.hub` 클래스, 그 외는 `boardingsPerDay` 로 1.6~4.6px.
지표 계산에는 안 들어가므로 값이 늘거나 바뀌어도 안전합니다. 분류 기준은 `API_SPEC.md` 참고.

### 1.6 오류 바디는 키 이름이 자유롭다

프론트는 `message` → `detail` → `error` 순으로 찾아 사용자에게 표시하고,
JSON 파싱이 안 되면 평문을 그대로 씁니다(`api.js`). 서버가 어떤 형태로 주든 표시는 됩니다.

### 1.7 타임아웃

프론트가 요청을 끊는 마감시한입니다. 서버는 이 안에 답해야 합니다.

| 대상 | 제한 |
|---|---|
| `/recommendations` · `/reports/draft` | 120초 |
| 그 외 전부 | 15초 |

### 1.8 서버가 아직 안 주는 것 — 어댑터가 보충 중

`api.js` 의 어댑터가 **빠진 키만** 채웁니다. 서버가 채워 보내기 시작하면 어댑터는 자동으로 물러납니다.

| 필드 | 상태 |
|---|---|
| `/simulations` 의 `effectiveness.resolvedElderlyTripsPerDay` | 서버 미구현 — 어댑터가 `delta` 로 보충 |
| `/recommendations` 의 `placements[].rationale` | 서버 미구현 — 오면 배치 항목 아래 회색 문장(`.why`)으로 그대로 렌더 |

`rationale` 은 수요지수·공급지수·커버리지 수치를 근거로 한 **한 문장**을 기대합니다.

## 2. 설계 근거 — 왜 그렇게 정했나

### 2.1 왜 총사업비로 비교하는가

수단마다 비용의 성격이 다릅니다 — 정류장은 1회성 시설비, 똑버스·증편은 연간 운영비.
어느 자로 잴지 정해야 하고, **총사업비**를 골랐습니다.

처음에는 연환산을 썼는데, 그러면 정류장이 연 420만 원 vs 똑버스 연 1.8억 원으로
**43배 싸게** 잡혀 추천이 정류장으로 쏠렸습니다.

*(아래는 목 데이터 기준 · 예산 30억 · 출근 · 20건 요청. 현행 실데이터 수치가 아닙니다.)*

| 비교 기준 | 정류장 | 똑버스 | 증편 | 집행액 | 예산 소진 | 해소 격자 | 해소 통행 |
|---|---|---|---|---|---|---|---|
| 연환산 (정류장만 ÷10년) | **17** | 2 | 1 | 11.7억 | 39% | 22칸 | 39,246 |
| 연환산 (똑버스도 ÷8년) | 9 | 11 | 0 | 23.6억 | 79% | 28칸 | 45,471 |
| **총사업비 (채택)** | 10 | 9 | 1 | **21.4억** | 71% | **28칸** | **45,471** |

총사업비를 고른 이유는 결과가 좋아서가 아니라 **기준이 맞아서**입니다.

1. **예산 한도를 총액으로 재고 있었습니다.** 채택 여부는 `spent + cost > budget`(총액)으로
   자르면서 순위는 연환산으로 매기고 있었습니다. 재는 자와 자르는 자가 달랐던 것이고,
   이게 쏠림의 직접 원인입니다. 화면 예산 입력칸도 총액(억 원)입니다.
2. **공무원이 실제로 묻는 것**은 "올해 예산 30억으로 무엇을 살 수 있나"입니다.
3. **가정이 하나 줄어듭니다.** 내용연수를 정하지 않아도 됩니다. 위 표에서 보듯 똑버스
   내용연수를 8년으로 잡느냐 마느냐로 결과가 크게 흔들리는데, 그 값 자체가 근거 없는 가정이었습니다.

> **한계 — 총사업비는 1년차 관점입니다.** 정류장은 한 번 지으면 끝이지만 똑버스·증편은
> 이듬해에도 같은 예산이 듭니다. 다년도로 비교하면 정류장 비중이 다시 커집니다.
> 이 한계는 화면(추천 박스 하단)과 보고서 주석에 그대로 표시됩니다.

가운데 행(똑버스도 ÷8년)이 이 표의 핵심입니다. 그 한 행이 이유 ③의 근거이고,
다른 문서에는 없습니다.

### 2.2 전략 수용 기준 — 자기 지표에서 1위여야 한다

`includeAlternatives` 로 네 전략을 나란히 놓고 **해소 격자 · 일 통행 · 고령 통행 ·
사업비 · 읍면동 수** 5열을 비교합니다.

| 전략 | 1위여야 하는 지표 |
|---|---|
| 효율 최우선 | 일 통행 |
| 교통약자 우선 | 고령 통행 |
| 지역 균형 | 읍면동 수 |
| 즉시 착수 | 최저 사업비 |

**자기 지표에서 1위가 아닌 전략은 존재 이유가 없습니다.** 그러면 목적함수를 다시 봐야 합니다.

### 2.3 수단 게이트는 매 회차 갱신된 커버리지로 판정한다

기준선 커버리지로 판정하면 이미 정류장을 놓은 격자가 계속 `stop` 구간에 남습니다.
매 회차 다시 계산한 커버리지로 게이트를 통과시켜야 합니다.

### 2.4 수단 성격 — 넓고 얕게 vs 좁고 깊게

똑버스는 반경을 넓게 잡고 격자당 효과는 얕게, 정류장 신설은 좁게·깊게 갑니다.
물리 파라미터의 정본은 `API_SPEC.md` §7 입니다.

### 2.5 정류장 ID 를 결합키로 둔 이유

`{시군구코드}-{ARS번호}` 형태로 둔 것은 **나중에 인접 시군으로 확장해도 키를 갈아엎지
않기 위해서**입니다(ARS 번호는 시군구 안에서만 유일합니다).

## 3. 해봤다가 안 된 기록

### 3.1 교통약자 우선 — 가중치를 올리는 방식은 통하지 않는다

처음에 교통약자 우선 전략을 "고령 가중 1.6 → 3.0" 으로 만들었더니 상위 5건이
효율안과 **완전히 동일**했습니다. 격자 간 고령비 차이가 작아 순위가 안 바뀝니다.
**기준 자체를 고령 통행량으로 바꿔야** 실제로 다른 답이 나옵니다.

> **아직 다 적용되지 않았습니다.** 2026-08-13 실서버에서 출근·30억·5건으로 돌리면
> efficiency · equity · balance 의 요약이 여전히 완전히 같습니다. 고령 통행이 가장 큰 안은
> 오히려 즉시 착수(quick)입니다. 위 교훈이 남은 전략에도 적용돼야 합니다.

## 4. 미채택 선택지

**서버측 `.hwpx` 생성** — 필요해지면 `python-hwpx` · `pyhwpx` · 한컴 오피스 SDK 를
검토할 것. 현재는 브라우저에서 `.rtf` 로 우회합니다(한컴오피스에서 열어 `.hwp` 로 다시 저장).

## 5. 연동 자가진단

화면이 이상할 때 원인을 좁히는 두 가지입니다. 둘 다 오류가 안 나서 눈치채기 어렵습니다.

**지도에 격자가 안 칠해진다** → 원인은 둘뿐입니다.
`cells[].bins` 누락(§1.1 의 균일 폴백) 또는 `lon`/`lat` 이 `meta.grid.bbox` 밖
(bbox 기준 선형 투영이라 화면 밖으로 나갑니다).

**네 시간대의 KPI 가 전부 같다** → `period` 가 계산에 안 먹은 것입니다.
수요 z 는 시간대에 거의 불변이라 시간축 차이는 공급 쪽에서 생깁니다 — 공급 재계산이
빠졌는지 보세요.
