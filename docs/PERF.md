# 지도 렌더 성능 — 무엇이 느렸고, 어떻게 고쳤나

「노선이 모여 있는 곳에서 지도를 끌면 버벅인다」에서 시작해 여섯 군데를 고친 기록입니다.
**모든 수치는 실측입니다.** 재현 방법은 §2 에 있고, 틀렸던 가설과 제가 만들었다가
되돌린 회귀도 §3·§9 에 그대로 남겨 뒀습니다 — 다음 사람이 같은 데서 넘어지지 않게.

관련 커밋: `1f485d4` · `4c61a34` · `1aa2261` · `acb38fa` · `ae9cfc8`

## 2. 어떻게 쟀나 — 이걸 먼저 읽으세요

수치보다 **재는 방법**이 중요합니다. 이 문서의 숫자 대부분은 처음에 잘못 쟀다가
방법을 고친 뒤에야 안정됐습니다.

### 환경

```
chromium_headless_shell · 1440×900 · 백엔드 127.0.0.1:8000 · 프론트 127.0.0.1:5500
확대 지점은 노선이 가장 빽빽한 동탄 부근(지도 폭 74% · 높이 46%)
zdetail 측정은 휠 12노치 = 1,455% (--zk 14.552), 카카오 배경·점선이 켜진 상태
```

### 함정 1 — CDP 왕복 지연이 프레임 간격을 오염시킵니다

`page.mouse.move()` 는 호출마다 브라우저와 왕복합니다. 그 사이 페이지는 놀고 있는데
`requestAnimationFrame` 타이머는 계속 도니까, 프레임 간격에 왕복 지연이 섞여 들어갑니다.
처음에 이렇게 재서 "전체 배율 med 83ms · zdetail med 150ms" 같은 값이 나왔고,
층을 꺼 봐도 차이가 안 보였습니다.

**드래그를 페이지 안에서 합성하세요.** 실제 핸들러는 그대로 돕니다.

### 함정 2 — 드래그 사이에 `<style>` 을 넣었다 빼면 다음 드래그까지 오염됩니다

A/B 를 한 세션에서 번갈아 하려고 매번 스타일을 삽입·제거했더니, 그 자체가 스타일
재계산과 재래스터를 부르고 뒷 드래그에 남았습니다. 같은 조건이 **116.6ms 와 166.6ms
사이를 오갔습니다.** 변종마다 페이지를 새로 띄우니 6/6 회 116.7ms 로 딱 떨어졌습니다.

### 함정 3 — 워밍업 없이 첫 드래그를 쓰면 안 됩니다

첫 드래그는 183.2ms, 이후 다섯 번은 전부 116.6ms 였습니다. **2회 버리고 시작하세요.**

### 함정 4 — 상태를 확인하지 않으면 다른 화면을 재게 됩니다

한 번은 "드래그 50ms" 라는 좋은 수치가 나왔는데, 카카오 배경이 안 붙은 실행이라
`.kkmode.zdetail .rt` 의 점선 규칙이 적용되지 않은 상태였습니다. 점선이 비용의
대부분인데(§6) 그게 빠진 화면을 잰 것입니다. **잰 직후 상태를 함께 찍으세요.**

```js
const s = getComputedStyle(document.querySelector('.rt'));
({ kk:  map.classList.contains('kkmode'),      // 카카오 배경이 실제로 붙었나
   zd:  map.classList.contains('zdetail'),
   zk:  getComputedStyle(map).getPropertyValue('--zk'),
   dash: s.strokeDasharray })                  // 'none' 이면 점선이 안 걸린 화면
// 정상: {kk:true, zd:true, zk:'14.552', dash:'0.343595px, 0.274876px'}
```

### 함정 5 — 일을 rAF 로 옮기면 "핸들러 JS" 지표가 거짓말을 합니다

휠을 프레임당 한 번으로 합치고(§7) 나서 휠 핸들러 JS 를 다시 재니 **1,065ms → 0.3ms**
가 나왔습니다. 97% 가 아니라 99.97% 입니다. 물론 거짓입니다 — 일이 사라진 게 아니라
`requestAnimationFrame` 콜백으로 **옮겨 갔을 뿐**이고, 제 계측기는 핸들러 안만 재고
있었습니다.

일을 미루는 최적화를 하면 "그 함수에서 보낸 시간" 류의 지표는 전부 무의미해집니다.
**결과로 재세요** — 프레임 간격, 정착까지 걸린 시간, 최종 상태가 같은지.

### 함정 6 — 프레임 간격은 16.67ms 배수로 양자화됩니다

헤드리스도 vsync 에 묶여 있어 값이 16.7 / 33.4 / 50 / 66.6 / 83.3 / 100 / 116.7 /
133.4 / 166.6 / 200 으로만 나옵니다. **83.3 과 100 은 한 칸 차이(6프레임 vs 5프레임)**
지 "17% 차이"로 읽을 값이 아닙니다. 한 칸 이내 차이는 유의미하지 않다고 보세요.

### 함정 7 — 층별 표는 더해지지 않습니다. 잔차로 범인을 찾지 마세요

「한 층씩 꺼 보기」로 만든 표를 **가산적인 예산표처럼 읽으면 안 됩니다.** 확대 쪽
실측이 그 예를 그대로 보여 줍니다.

```
현재 700ms │ 카카오만 숨김 333ms(52%) │ 우리 SVG 통째로 숨김 317ms(55%)
                                        → 52 + 55 = 107% > 100%
격자 제거 550ms(21%) 인데 느린 프레임 **개수**는 8개로 오히려 늘었다(현재 7개)
노선 제거는 단독으로 0% 인데, 카카오와 함께 빼면 83ms 가 더 준다(교호작용)
```

층을 끄면 그 층의 비용만 사라지는 게 아니라 **합성·오버드로 구조 자체가 달라집니다.**
그래서 "L 이 55% 니까 나머지 45% 는 어딘가에 있다" 같은 잔차 계산이 성립하지 않습니다.
실제로 저는 이 잔차(≈190ms)를 근거로 바탕 층(`.wtr` 전면 사각형·`.land` 채움)을
범인으로 지목했는데, 재 보니 **숨기면 오히려 3% 느려졌습니다.** 가설이 틀린 게 아니라
**가설을 만든 방식이 틀렸습니다.**

같은 이유로 **반복 4회는 부족합니다.** 위 격자 21%는 쌍 반복에서 차의 부호가
−84 / +83 / +100 으로 뒤집혔습니다 — 즉 실재하지 않는 효과였습니다.

> **규칙** — 층별 비교는 같은 쌍을 **8회 이상** 반복하고, 쌍별 차의 **부호가 한 번이라도
> 뒤집히면 "이득 0"으로 기록**하세요. 그리고 표의 항목끼리 더하거나 빼서 새로운
> 결론을 만들지 마세요. 궁금하면 그 조합을 **직접 재세요**(위 K 행처럼).

### 재는 코드

```js
// 페이지 안에서 실행. 실제 pointermove 핸들러가 그대로 돕니다.
window.__drag = async function () {
  const svg = document.querySelector('#map'), r = svg.getBoundingClientRect();
  const x0 = r.left + r.width * 0.5, y0 = r.top + r.height * 0.5;
  const ev = (t, x, y) => svg.dispatchEvent(new PointerEvent(t, {
    clientX: x, clientY: y, button: 0, buttons: 1,
    pointerId: 1, isPrimary: true, bubbles: true, cancelable: true }));
  const mv = (x, y) => svg.dispatchEvent(new MouseEvent('mousemove', {
    clientX: x, clientY: y, bubbles: true }));      // 정류장 판정 경로도 함께 돌리려고
  const frames = []; let last = 0;
  ev('pointerdown', x0, y0);
  const path = [];
  for (let i = 0; i <= 36; i++) path.push([x0 - i * 4, y0 + Math.sin(i / 6) * 18]);
  for (let i = 36; i >= 0; i--) path.push([x0 - i * 4, y0 + Math.sin(i / 6) * 18]);
  for (const [x, y] of path) {
    await new Promise(rs => requestAnimationFrame(t => {
      if (last) frames.push(t - last); last = t; rs(); }));
    ev('pointermove', x, y); mv(x, y);
  }
  ev('pointerup', x0, y0);
  return frames;      // 중앙값을 쓰세요. 워밍업 2회 버리고 6회 이상.
};
```

층별로 비용을 가를 때는 **한 층씩 끄면서** 같은 드래그를 돌리면 됩니다
(`#map [data-groutes]{display:none}` 처럼). 이게 §6 의 표를 만든 방법입니다.

## 3. 진단이 먼저 — 제 첫 가설은 틀렸습니다

처음에는 JS 를 의심했습니다. 노선 문자열을 두 번 만드는 것, `toFixed`, `project()`
상수 재계산. 실제로 재 보니 그쪽에도 낭비가 있긴 했습니다.

```
경로 문자열 2회 생성  35.6ms  →  1회  17.1ms  →  toFixed 없이  9.9ms
문자열 +=  4.8ms   vs   배열 join  5.3ms      ← join 이 더 느림, 기각
```

그런데 **팬 프레임 비용의 95% 가 JS 가 아니라 브라우저 페인트/래스터**였고,
결정적으로 **팬 중에 `gRoutes.innerHTML` 대입은 0회**였습니다. 즉 위 최적화는
드래그할 때 아예 실행되지도 않는 코드였습니다.

> **교훈** — "느린 것 같다" 로 코드를 고치지 말고, 먼저 **JS 인지 페인트인지** 가르세요.
> JS 라면 어느 함수가 몇 번 도는지 세고, 페인트라면 층을 하나씩 꺼 보세요.
> 이 문서의 나머지는 전부 후자였습니다.

## 4. 격자 호버 — `filter` 한 줄이 지도 전체를 다시 칠하고 있었습니다

### 문제

```css
.cells rect:hover { filter: saturate(1.5) brightness(1.07) }   /* 지금은 없습니다 */
```

`filter` 는 그 요소를 **별도 페인트 서피스로 승격**시킵니다. 마우스가 칸 하나를
넘을 때마다 지도 전체가 다시 래스터됐습니다.

```
호버 프레임 p95 118.5ms · 최대 201.6ms · 50ms 초과 6/72
```

### 해결

밝기 강조를 호버 레이어 맨 위의 **반투명 사각형 한 장**으로 냅니다(`.hov-fill`).
`map.js` 의 `placeHoverRing` 이 이 사각형을 가리킨 칸에 맞춰 옮깁니다.

```css
.hov-fill { fill:#fff; fill-opacity:.14; stroke:none }
:root[data-theme="light"] .hov-fill { fill:#000; fill-opacity:.07 }
```

**테마마다 방향이 반대입니다.** 다크는 흰 덮개로 띄우고, 라이트는 검은 덮개로
누릅니다. 라이트에서 흰 덮개를 쓰면 이미 밝은 칸이 더 옅어지는데, **발산형 색
스케일에서는 그게 "값이 낮다"로 읽힙니다** — 지표를 반대로 읽게 만드는 버그입니다.
스크린샷으로 확인하고 고쳤습니다. 어느 쪽이든 색상(hue)은 안 건드리므로
"색을 바꾸면 지표를 잘못 읽게 된다"는 `app.css` 의 기존 계약은 지켜집니다.

### 결과

```
p95 118.5 → 25ms · 최대 201.6 → 55ms · 50ms 초과 6 → 1
3회 반복: 24.9 / 23.7 / 26.3ms
```

### 정확히 무엇이 금지인가 — `filter` 자체가 아닙니다

이 문서를 쓰면서 확인해 보니 `app.css` 에는 격자에 걸린 `filter` 가 **아직 하나 더**
있습니다. 영역을 고르는 중 선택된 칸에 붙는 규칙입니다.

```css
.cells rect.indraft { filter: saturate(1.45) brightness(1.05) }   /* 남아 있습니다 */
```

같은 함정일까 싶어 칸 수를 늘려 가며 쟀는데, **비용이 없었습니다.**

```
indraft   0칸 → 83.2ms      indraft  60칸 → 66.7ms
indraft  10칸 → 66.7ms      indraft 300칸 → 83.2ms
```

전부 한 vsync 칸(§2 함정 6) 안이라 차이라고 부를 수 없습니다. 이유는 분명합니다 —
`.indraft` 는 **정적인 클래스**라 한 번 래스터되고 나면 팬할 때 그냥 따라 움직입니다.
`:hover` 가 재앙이었던 건 필터가 **마우스가 움직일 때마다 다른 칸으로 옮겨 다녀서**
매 프레임 승격과 재래스터를 새로 일으켰기 때문입니다.

> ⚠️ **금지 대상은 "빠르게 바뀌는 상태에 걸린 `filter`·`opacity`"** 입니다.
> `:hover`, 드래그 중 따라다니는 강조, 애니메이션 중 토글되는 클래스가 여기 해당합니다.
> 정적인 선택 표시라면 써도 됩니다 — 다만 **재고 나서** 쓰세요.
> `app.css` 의 `.hov-fill` 위치에 경고를 남겨 뒀습니다.

## 5. 정류장 이름표 — 2,866개가 매 프레임 재레이아웃 대상이었습니다

### 문제

SVG `<text>` 는 **viewBox 가 바뀔 때마다 전부 다시 재는** 대상입니다. 예전에는
이름표 2,866개를 통째로 만들어 두고 CSS 로만 감췄습니다. 확대해 둔 채 팬하면
프레임마다 2,866개 텍스트를 다시 쟀습니다.

```
프레임당 레이아웃 248ms  →  이름표를 빼면 2.7ms (−99%)
```

게다가 `zdetail` 임계를 넘을 때마다 `renderRoutes` 가 통째로 돌아 노선 200개 +
정류장 2,866개(**59만 자**)를 재파싱했습니다.

### 해결

이름표를 **별도 층**(`<g data-gstoplab>`)으로 떼고, **지금 화면에 드는 것만** 만듭니다.

- 갱신은 움직임이 멈춘 뒤 **120ms 디바운스** → 프레임당 비용 0
- 이름표는 SVG 좌표라 viewBox 와 함께 따라 움직이므로, 움직이는 동안 갱신하지
  않아도 어긋나지 않습니다. 새로 드러나는 가장자리는 **20% 여유 마진**이 덮습니다.
- 층이 나뉘어서 `zdetail` 임계를 넘을 때 노선·정류장을 재파싱하지 않고
  이름표 층만 갈아끼웁니다.
- 격자 포커스 상태(`.always`)는 몇 개뿐이라 컬링하지 않습니다.

### 결과

```
이름표 2,866 → 60개 (zdetail 진입 시) → 23개 (더 확대)
zdetail 팬  204 → 105ms (−48%)

같은 세션 교차 3회:
  컬링   107.3 / 106.3 / 102.4ms  (33개)
  전체   206.8 / 204.9 / 201.2ms  (2,866개)
```

## 6. 확대 상태 드래그 — 범인은 점선이었습니다

여기가 원래 질문("확대된 지도를 마우스로 끌 때 버벅인다")의 답입니다.

### 진단 — 층을 하나씩 껐습니다

zdetail(1,455% · 동탄 · 카카오 배경·점선 켜짐 · 프레임 간격 중앙값):

| 끈 것 | 프레임 | |
|---|---|---|
| (없음, 현재) | 200ms | |
| **노선 층 전체** | **33ms** | **−83%** |
| **점선만 해제** | **83ms** | **−58%** |
| 케이싱 | 200ms | 0% |
| 정류장 점 | 200ms | 0% |
| 이름표 | 200ms | 0% |
| 격자 | 200ms | 0% |
| 카카오 배경 | 200ms | 0% |
| `shape-rendering:optimizeSpeed` | 200ms | 0% |

**비용은 사실상 전부 노선 층이고, 그중 대부분이 점선입니다.**

### 왜 점선이 그렇게 비싼가

점선 개수는 `경로 길이 ÷ 점선 주기` 입니다. 주기를 `--zk` 로 역스케일해 화면상
굵기를 유지하니 **확대할수록 잘게 쪼개집니다** — 14.5배에서 5px 가 0.34
사용자단위가 됩니다(실측 `stroke-dasharray: 0.343595px, 0.274876px`).

여기에 결정적인 조건이 하나 더 붙습니다. **노선 200개는 저마다 시 전체를 가로지르는
폴리라인 하나**입니다. 화면에 0.5% 만 걸쳐 있어도 브라우저는 **경로 전체 길이만큼**
점선을 셉니다.

### 해결 — 창 밖 구간을 잘라 냅니다

점선을 없애면 −58% 를 벌지만, `app.css` 에 적힌 주장을 잃습니다:

> 노선 선은 정류장을 순서대로 이은 **모식도**지 실제 도로 형상이 아닙니다.
> TAGO/경기도 API 가 경유정류소 목록만 주고 폴리라인을 주지 않아서입니다.
> 확대해 실제 도로가 보이는 상태에서 실선으로 두면 "버스가 이 길로 간다"는
> **틀린 주장**이 됩니다.

그래서 점선은 두고 **화면 밖 구간을 잘라 냅니다.** 같은 이득이 납니다.

- `<g data-groutes>` 를 **노선 선 / 정류장** 두 층으로 쪼갬 — 노선만 다시 깎을 때
  정류장 2,866개까지 재파싱하지 않게. 부모는 그대로라 `display`·`fathit`·`nohit`
  상태와 CSS 선택자는 손대지 않았습니다.
- 창 사방에 **제 크기만큼 여유**(`RT_PAD = 1.0`)를 두고 잘라 두었다가, 그 여유를
  벗어났을 때만 다시 깎습니다 → 드래그 한 번(74스텝)에 **재클립 0회**.
- 자른 조각은 점선 위상이 그 자리에서 다시 시작합니다. 그대로 두면 다시 깎는
  프레임마다 **화면 안 점선이 통째로 최대 9px 튑니다**(케이싱 실선은 안 움직이니
  그 위를 미끄러집니다). 노선 시작점부터의 거리를 `stroke-dashoffset` 으로 되돌려
  어디서 자르든 점선이 원래 자리에 놓이게 했습니다.

### 결과

```

노선 폴리라인       200 → 152개
노선 층 DOM         59만 자 → 3.8만 자
드래그 중 재클립     0회
점선 위상 검증       재클립 전후 공통 좌표 168개 · 위상 차이 0.00
클립 1회 비용        9.8ms
```

## 7. 휠 확대·축소 — 배율이 바뀌면 같은 코드가 30배 비싸집니다

「정류장 많은 곳에서 **확대·축소**할 때도 버벅인다」로 들어온 별건입니다.
팬과 원인이 전혀 달랐습니다.

### 문제 — 한 줄이 휠 처리 JS 의 95%

```js
function toSvgXY(e) {
  var r = svg.getBoundingClientRect();   // ← 여기
```

커서 위치를 지도 좌표로 바꾸려고 상자 좌표를 읽습니다. 그런데 바로 앞에서
`applyZoom` 이 `viewBox` 와 **`--zk`** 를 써 놓았고, `--zk` 는 CSS 19개 규칙·26곳에서 점·선·글자
크기를 역스케일하는 데 쓰입니다. 그래서 이 읽기 한 번이 **SVG 전체의 스타일 재계산과
레이아웃을 그 자리에서 끝내게** 만듭니다(강제 동기 레이아웃).

게다가 휠은 한 프레임에 여러 개가 몰려 들어오는데 스로틀이 없어, 그때마다 이 일을
처음부터 다시 했습니다.

```
휠 이벤트당 81.7ms · 12노치 버스트에서 980.8ms = 휠 처리 JS 전체의 95%
그동안 실제로 그려진 프레임은 5개
```

> **핵심** — 같은 `getBoundingClientRect` 가 팬에서는 **2.8ms** 입니다.
> **배율이 바뀌느냐가 30배를 가릅니다.** 팬은 `viewBox` 만 바꾸므로 `--zk` 에
> 매달린 요소들이 안 깨집니다. §8.1 에서 팬 쪽 같은 패턴을 이미 고쳤는데도
> 휠에서 이게 남아 있던 이유가 이것입니다 — **팬만 보고 있었습니다.**
> 「무엇을 무효화하는가」를 보지 않고 「어떤 함수를 부르는가」만 보면 놓칩니다.

### 해결 1 — 상자 좌표를 한 프레임 동안만 캐시

같은 프레임 안에서는 상자가 움직일 수 없으니 버스트 전체가 한 번만 읽으면 됩니다.
프레임이 바뀌면 버립니다 — 사이드바가 접히거나 스크롤돼 옮겨졌을 수 있습니다.

**`ResizeObserver` 만 거는 것으로는 부족합니다.** 크기는 그대로인데 위치만 밀리는
경우(스크롤, 위쪽 요소의 높이 변화)를 못 잡습니다. 프레임 단위 자동 폐기가
그 경우까지 덮으면서 버스트 안에서는 한 번만 읽게 해 줍니다.

### 해결 2 — 휠을 프레임당 한 번으로 합침

이벤트마다 `applyZoom` 을 부르면 그 프레임에는 마지막 것 하나만 화면에 나오는데도
12번을 다 계산합니다(카카오 `setBounds` 만 12회 19.7ms). 배율을 곱해 모아 두었다가
프레임당 한 번 적용합니다.

**결과가 같은 이유** — 같은 프레임 안에서는 `zoom` 이 안 바뀌므로 이벤트마다
`toSvgXY` 가 내놓는 지도 좌표가 전부 같습니다. 커서 고정 확대는 같은 기준점에 대한
곱셈이라 결합법칙이 성립하므로, 한 번에 `1.25¹²` 를 적용한 것과 한 노치씩 12번
적용한 것이 같습니다.

### 결과

```
휠 처리 JS 총량 (12노치)      확대                축소
  버스트              1,065.5 → 34.6ms    1,189.9 → 128.9ms
  실속도(50ms 간격)     346.6 → 75.9ms      469.8 → 192ms

버스트 프레임                 확대                축소
  중앙값                116.7 → 66.7ms       16.7 → 16.7ms
  p95                   366.5 → 166.7ms  1,266.6 → 116.6ms
  정착까지              1,730 → 702ms      1,872 → 701ms
```

> ⚠️ **느린 마우스 휠(50ms 간격)은 원래도 문제가 없었습니다**(프레임 중앙값 16.7ms)
> **그리고 지금도 같습니다.** 이 절이 고치는 것은 트랙패드나 빠르게 굴릴 때처럼
> 이벤트가 한 프레임에 몰려 들어오는 경우입니다. 축소 p95 1,266ms 가 그 증상입니다.
> 느리게 한 칸씩 굴릴 때도 버벅인다면 원인이 여기가 아닙니다.

### 좌표가 어긋나지 않는지 — 이건 꼭 확인해야 합니다

캐시한 상자로 커서를 지도 좌표에 옮기므로, 여기가 틀리면 **확대 지점과 클릭 위치가
통째로 밀립니다.** 휠 확대의 '커서 고정' 성질로 검증합니다 — 커서 밑에 있던 지도
지점은 확대해도 그 자리에 있어야 합니다.

```
                        dx        dy
스크롤   0px        -1.65px   -2.72px
스크롤 300px        -1.65px   -2.72px    ← 캐시가 제때 버려짐(값이 안 변함)
적용 전(1aa2261)    -1.65px   -2.72px    ← 완전히 동일
```

이 2px 대 드리프트는 `clampBox` 에서 오는 **기존** 것이고 이 변경과 무관합니다.
12노치 뒤 최종 배율 14.552 · zdetail 진입 · 노선 152조각 · 이름표 76 — 전부 전과 같습니다.

**한 번 놀란 것** — 느린 휠로 확대한 직후에는 노선 조각이 152개가 아니라 301개였습니다.
회귀인가 싶었는데, 미뤄 둔 재클립(§9.1 의 `routeClipLoose`)이 곧 152개로 조여 주는
과도 상태였습니다. 조인 뒤 드래그는 83.4ms 로 동일합니다.

### 그 다음 — 남은 절반은 어디이고, 왜 못 줄였나

위까지 하고 나서 "배율 쪽에 더 할 게 있나" 를 따로 조사했습니다. 결론은 **거의
없습니다.** 남은 비용이 어디인지는 확실해졌으니 그것만 적어 둡니다.

층을 끄며 재면(12노치 버스트, 20ms 넘는 프레임의 시간 합):

```
현재 700ms │ 카카오 배경만 숨김 333ms │ 우리 SVG 통째로 숨김 317ms
  → 배경과 우리 SVG 가 거의 반반. 어느 한쪽이 범인이 아닙니다.
우리 SVG 안에서는 노선 0% — 팬에서 83% 였던 것과 정반대입니다(§6).
```

카카오 쪽 58점 중 **49점이 `setBounds`** 였습니다. 카카오는 정수 줌 레벨로만
반응해서 휠 한 칸마다 레벨을 다시 고르고 타일 세트를 갈아 끼웁니다.

```
setBounds 무력화     확대 283ms(+49%) · 축소 167ms(+41%)
아핀 transform 고정   확대 500ms( +9%)      ← 우리가 거는 CSS 변형은 9점뿐
```

**그래서 제스처 중 `setBounds` 를 미루는 안을 실제로 구현해 봤고, 되돌렸습니다.**
굴리는 동안에는 이미 그려 둔 타일에 아핀만 다시 걸고, 멈추면 한 번 진짜로 맞추는
방식입니다(축소할 때 배경이 프레임보다 작아져 빈 띠가 생기는 함정은, 아핀을 먼저
계산해 프레임을 덮는지 보고 안 덮으면 즉시 `setBounds` 하도록 막았습니다).

설계대로 정확히 동작했습니다 — **`setBounds` 호출이 확대 12→1회, 축소 12→5회.**
그런데 **프레임 비용은 안 줄었습니다: 버스트 0% · 실속도 −5%.**

- 버스트는 앞의 rAF 합치기가 **이미 1회로 줄여 놔서** 미룰 것이 없었습니다.
- 실속도에서는 타일 작업 **총량이 같고 시점만 뒤로 밀릴** 뿐이었습니다.
- `setBounds` 무력화가 +49% 였던 것은 **타일을 아예 안 그렸기 때문**이지
  호출 횟수를 줄여서가 아닙니다. 호출 수와 비용은 비례하지 않습니다.

프로젝트에서 가장 민감한 코드(카카오 정합)를 건드려 5% 를 살 이유가 없어
되돌렸습니다. **남은 비용은 배경 타일 렌더링이고, 배경을 포기하지 않는 한
줄일 수 없습니다.**

> 이 조사에서 얻은 진짜 소득은 최적화가 아니라 **§2 함정 7**(층별 표는 더해지지
> 않는다 · 4회 반복은 부호가 뒤집힌다)과, 아래 §8.5 의 표현 버그였습니다.

## 8. 그 밖에 고친 것

### 8.1 드래그 경로의 강제 동기 레이아웃 2건

`applyZoom` 이 `viewBox` 를 써서 레이아웃을 막 더럽힌 **직후 같은 호출 스택에서**
화면 좌표를 읽고 있었습니다(write → read 레이아웃 스래싱). 실측 **호출당 2.8ms**,
드래그 187회에 372회 호출(이벤트당 2회)이었습니다.

- `pointermove` 의 `svg.getBoundingClientRect()` → 상자 위치는 끄는 동안 변하지
  않으므로 **`pointerdown` 에 한 번만** 재서 캐시(`panRect`).
- 끄는 중에도 `mousemove` 의 정류장 판정이 돌아 같은 읽기를 한 번 더 하고,
  히트 층이 없는 전체 표시 상태에서는 `nearestStop` 이 2,866개를 좌표로 훑었습니다.
  → **끌고 있을 때는 건너뜁니다.** 어차피 툴팁을 띄울 상황이 아닙니다.

### 8.2 `alignKakao` 도 같은 패턴

`applyZoom` 직후 `kkInner.clientWidth` 를 읽고 있었습니다. 컨테이너 크기는 팬 중에
변하지 않는데 매 이벤트 다시 물었습니다. **`ResizeObserver` 가 이미 크기 변화를
감시하므로 그 값을 캐시해 씁니다.**

```
휠 핸들러 JS 중앙  106 → 3ms
휠 12회 합계      1,790 → 221ms
```

이건 프레임이 아니라 **입력 지연 예산**입니다 — p95 프레임 수치는 이 항목으로
안 내려갑니다.

### 8.3 이름표가 유령으로 남던 버그

§5 에서 이름표를 별도 층으로 뗐는데, `renderRoutes` 의 조기 반환이 `gRoutes` 만
비우고 **이름표 층은 그대로 뒀습니다.** 격자를 찍어 이름표가 떠 있는 상태에서
노선을 끄면 정류장 점은 사라지고 **이름 41개가 빈 지도 위에 남았습니다.**
격자 재클릭 해제에서 재현됩니다(정류장 0개 · 이름표 41개). 같이 지웁니다.

> 층을 나눌 때는 **지우는 경로도 같이 나눠야** 합니다. 이게 §5 최적화의 대가였습니다.

### 8.4 전체 배율 드래그 — 정지 화면은 그대로 두고

§6 의 클리핑은 전체 뷰에서 아무것도 못 자릅니다. 화면 밖이 없으니까요.
전체 배율은 200ms 그대로였고, 남은 비용은 역시 노선 층이었습니다.

| | 프레임 | |
|---|---|---|
| 현재 | 200ms | |
| 케이싱 끔 | 166.6ms | −17% |
| `optimizeSpeed` | 183.3ms | −8% |
| `crispEdges` | 183.3ms | −8% |
| 둘 다 | 133.4ms | −33% |
| 노선 층 통째로 끔 (하한) | 66.6ms | −67% |

둘 다 화면이 하는 주장을 깎습니다 — 케이싱은 붉은 칸 위에서 노선이 끊겨 보이지
않게 하는 대비 장치고, `optimizeSpeed` 는 안티에일리어싱을 꺼 선을 계단지게 합니다.
**33% 를 벌자고 정지 화면(캡처하고 발표에 띄우는 바로 그 화면)을 상시로 깎을
이유는 없습니다.**

그래서 **끄는 동안에만** 겁니다. `.panning` 은 `pointermove` 가 4px 이상 움직였을 때
붙고 손을 떼면 바로 떨어집니다.

```css
.panning .rt         { shape-rendering: optimizeSpeed }
.panning .rt-casing  { display: none }
```

움직이는 중에는 가장자리 계단이나 케이싱 유무를 눈이 잡지 못하고, 손을 떼는 순간
원래 품질로 돌아옵니다. 결과는 **상시 적용보다 오히려 낫습니다.**

```
전체 배율   200 → 116.7ms  (−42%, 6/6 회 동일)     ← 상시 적용판은 133.4ms
zdetail    83.4 → 83.3ms  (변화 없음, 예상대로)
```

zdetail 이 0% 인 것은 예상대로입니다 — 거기서는 케이싱이 원래 비용의 0% 였고
이미 클리핑이 처리했습니다.

### 8.5 읍면동 경계선이 확대할수록 사라지던 것 (성능 아님)

배율 쪽에 더 줄일 게 있나 조사하다 나온 **표현 버그**입니다. `.dongline` 에
`vector-effect:non-scaling-stroke` 와 `stroke-width:calc(1.1px/var(--zk,1))` 가
함께 걸려 있었습니다. `non-scaling-stroke` 를 쓰면 `stroke-width` 가 **이미 화면
픽셀**이라 배율로 나눌 필요가 없는데, 거기서 또 나눠 두 번 축소됐습니다.

```
화면상 굵기   1배 1.100px · 3.8배 0.288 · 7.5배 0.148 · 14.5배 0.076px
              (여기에 stroke-opacity .5 까지 곱해집니다)
```

바로 위 주석이 "어디까지가 어느 동인지 보이게 합니다" 인데, **들여다보려고
확대하면 그때 없어졌습니다** — 표현이 필요한 바로 그 순간에.

굵기를 고정값 `1.1px` 로 둡니다. 전체 배율에서는 `--zk` 가 1 이라 예전과 같은
1.1px 이므로 **첫 화면은 한 픽셀도 안 바뀝니다.**

> `vector-effect:non-scaling-stroke` 와 `--zk` 역스케일은 **같은 일을 하는 두 방법**입니다.
> 한 요소에 둘 다 걸면 두 번 적용됩니다. 이 파일에서 `non-scaling-stroke` 를 쓰는
> 다른 규칙은 `.area-box` 하나인데 그쪽은 `stroke-width:1.5` 로 올바릅니다.

## 9. 제가 만들었다가 되돌린 회귀 2건

최적화가 **다른 동작을 망가뜨리는지** 따로 검증하지 않으면 이런 게 남습니다.
둘 다 15명분의 적대적 검토(관점 5 × 반증 3표)로 잡았습니다.

### 9.1 축소할 때 노선 층을 3~4번 다시 만들고 있었습니다 (high)

클리핑 첫 판은 "다시 깎을까" 판정에 **배율 조건**을 같이 넣었습니다
(`zoom.w > _rtW*1.8 || zoom.w < _rtW*0.5`). 그런데 `applyZoom` 이 이걸 **그 자리에서
동기 실행**하고, `animateTo` 는 200ms 동안 매 프레임 `applyZoom` 을 부릅니다.

결과: **축소 애니메이션 한 번에 노선 층 innerHTML 이 3~4번 다시 만들어졌습니다.**
그중 뒤쪽 1~2번은 클립 상자가 이미 지도 전체를 덮어 **한 구간도 안 잘리는**,
화면상 달라지는 픽셀이 0인 재구축이었습니다 — 실측 **247,364자 → 247,364자, 바이트까지 동일**.
바꾸기 전 코드는 이 구간에서 노선 DOM 을 **한 번도** 안 건드렸으니 순수 회귀입니다.

**해결** — 판정을 성격에 따라 둘로 나눴습니다.

| | 무엇 | 언제 |
|---|---|---|
| `routeClipStale` | 창이 상자를 벗어나 **노선이 비어 보임** | 그 자리에서 (안 하면 "여기는 노선이 없다"는 틀린 주장) |
| `routeClipLoose` | 상자를 너무 넓게 잡아 **프레임이 비쌈** | 멈춘 뒤 140ms, **그때 다시 판정** |

추가로:
- `animateTo` 가 **애니메이션이 지나갈 구간(지금 창 ∪ 목표 창)** 을 미리 넘겨 한 번만
  깎습니다. 보간이 `x`·`w` 를 각각 선형으로 섞으므로 중간 창은 전부 이 합집합 안에
  들어옵니다 → **200ms 동안 재클립 0회.** 그 한 번의 비용은 클릭한 순간에 묻힙니다.
- 상자가 지도를 다 덮으면 결과가 '노선 전부'로 같으므로 **아예 건너뜁니다**
  (`routeBoxCoversAll`).
- 미뤄 둔 작업은 **실행 시점에 다시 판정**합니다. 축소 애니메이션의 앞 프레임들은
  '상자가 너무 넓다'로 보이지만, 끝나고 나면 창이 그 상자만큼 커져 있어 다시 깎아 봐야
  바이트까지 똑같은 전량 재구축이 됩니다.

```
축소 애니메이션 노선층 쓰기   3~4회 → 1회 (애니메이션 시작 전)
축소 애니메이션 프레임        216.7 → 16.7ms
확대(격자 클릭) 프레임                  16.7ms
```

### 9.2 재클립할 때마다 점선이 통째로 튀었습니다 (low)

§6 에 적은 `stroke-dashoffset` 이 이 검토에서 나왔습니다. 처음에는 "자른 자리는
창 밖이라 **화면은 그대로**"라고 주석에 썼는데, **거짓이었습니다.** 조각의 점선
위상이 0에서 다시 시작하니 다시 깎는 프레임마다 화면 안의 모든 점선이 한꺼번에
어긋났습니다.

> 최적화 주석에 "화면은 그대로" 라고 쓸 때는 **그걸 실제로 검증하고** 쓰세요.
> 검증 방법: 재클립 전후로 같은 좌표의 위상을 계산해 비교 (168개 · 차이 0.00).

## 10. 측정으로 기각한 것들

고치지 **않기로** 한 것도 기록해 둡니다. 다시 시도하지 않게.

| 아이디어 | 왜 기각했나 |
|---|---|
| 노선 문자열 배열 `join` 으로 바꾸기 | `+=` 4.8ms vs `join` 5.3ms — **더 느림** |
| 경로 문자열 생성 최적화 (2회→1회, `toFixed` 제거) | 팬 중에는 **실행되지 않는 코드** (`innerHTML` 대입 0회) |
| `shape-rendering:crispEdges` | `optimizeSpeed` 와 같은 −8%, 계단은 더 심함 |
| 점선을 아예 없애기 | −58% 를 벌지만 "노선은 모식도" 주장을 잃음. 클리핑이 **같은 값**을 공짜로 냄 |
| 케이싱·AA 상시 제거 | −33%. `.panning` 게이팅이 **−42% 를 손실 없이** 냄 |
| 정류장 점·격자·카카오 배경 손대기 | zdetail 팬에서 각각 **0%** |
| **제스처 중 카카오 `setBounds` 미루기** | 구현해서 재고 되돌림. 호출은 확대 12→1회로 줄었는데 **버스트 0% · 실속도 −5%**. 타일 작업 총량이 같고 시점만 밀릴 뿐 (§7 끝) |
| **확대 중 바탕 층(`.wtr`·`.land`) 숨기기** | 잔차 계산으로 세운 가설이었는데 재 보니 **오히려 −3%**. 가설을 만든 방식이 틀렸음 (§2 함정 7) |
| **확대에서 격자 손대기** | 4회 반복으로 21% 로 보였으나 쌍 차분 부호가 −84/+83/+100 으로 뒤집힘 → **실재하지 않는 효과** |

## 11. 남은 것

**전체 배율 팬 116.7ms 가 현재 바닥입니다.** 더 내리려면 노선 층 자체를 줄여야 하는데
(층을 통째로 끄면 66.6ms), 전체 뷰에서는 잘라 낼 화면 밖이 없습니다. 남은 길:

- **노선 단순화(Douglas–Peucker)** — 전체 뷰에서는 1 사용자단위 ≈ 1px 이라 정류장
  간격보다 촘촘한 점은 화면에 기여하지 않습니다. 좌표 9,471개를 줄일 여지가 있습니다.
  다만 확대하면 그 점들이 다시 필요해 배율별 캐시가 필요합니다.
- **팬을 viewBox 대신 CSS transform 으로** — 합성 레이어에 올리면 래스터 없이
  옮길 수 있지만, `--zk` 역스케일·히트 판정·카카오 정합이 전부 viewBox 를 전제로
  하고 있어 **파급이 큽니다.** 지금 값에 만족한다면 건드릴 이유가 없습니다.

**배율(휠) 쪽은 따로 조사해서 끝을 봤습니다 — 더 할 게 거의 없습니다.**
남은 700ms 는 카카오 배경과 우리 SVG 가 반반이고, 배경 쪽 58점 중 49점이
`setBounds`(정수 레벨이 바뀌며 타일을 갈아끼우는 값)입니다. 그걸 제스처 중에
미루는 안을 **실제로 구현해서 재고 되돌렸습니다** — 호출은 12→1회로 줄었는데
프레임은 안 줄었습니다(§7 끝). 배경 타일 렌더링 자체가 남은 비용이고,
배경을 포기하지 않는 한 줄일 수 없습니다.

즉 여기서 더 가려면 **배경을 끄거나(설계 후퇴), 우리 SVG 를 근본적으로 다시 그리는**
수밖에 없습니다. 후자를 굳이 본다면:

- **노선 단순화(Douglas–Peucker)** — 전체 뷰에서는 1 사용자단위 ≈ 1px 이라 정류장
  간격보다 촘촘한 점은 화면에 기여하지 않습니다. 좌표 9,471개를 줄일 여지가 있습니다.
  다만 확대하면 그 점들이 다시 필요해 배율별 캐시가 필요합니다.
  (팬에는 듣지만 **확대에는 안 듭니다** — 확대에서 노선은 0% 입니다.)
- **팬·확대를 viewBox 대신 CSS transform 으로** — 합성 레이어에 올리면 래스터 없이
  옮길 수 있지만, `--zk` 역스케일·히트 판정·카카오 정합이 전부 viewBox 를 전제로
  하고 있어 **파급이 큽니다.** 지금 값에 만족한다면 건드릴 이유가 없습니다.

두 화면 모두 확대 상태 드래그가 원래 문제였고, 그건 해결됐습니다.

## 12. 회귀가 의심될 때

```bash
node tools/check-css.js     # CSS 무언사(silent death) 검출 — 0 이어야 함
node tools/e2e-live.js      # 실서버 계약 38건
```

여기에 더해 이 문서의 최적화가 살아 있는지 보려면:

| 확인할 것 | 정상 값 |
|---|---|
| 호버 층이 있나 | `document.querySelector('.hov-fill')` 이 있고, 격자에 `filter` 가 **없음** |
| 이름표 컬링이 도나 | zdetail 에서 `.stlab` 이 **수십 개** (2,866개면 컬링이 죽은 것) |
| 노선 클리핑이 도나 | zdetail 에서 `.rt` 가 **152개 안팎** (200개면 클리핑이 죽은 것) |
| 점선 위상이 맞나 | `.rt[stroke-dashoffset]` 개수 == `.rt` 개수 |
| 드래그 게이팅이 도나 | 드래그 중 `.rt-casing` 이 `display:none`, 손 떼면 `inline` |
| 축소 애니메이션 | 노선 층 `innerHTML` 쓰기가 **1회** (3~4회면 §9.1 이 되돌아온 것) |
| 휠이 합쳐지나 | 한 프레임에 휠 12개를 던졌을 때 카카오 `setBounds` 호출이 **12회가 아니라 1회** |
| 휠 좌표가 맞나 | 휠 확대 뒤 커서 밑 지점이 **2px 대**로만 움직임. 스크롤한 상태에서도 같은 값 (§7) |

마지막 두 줄이 특히 중요합니다. **휠 좌표는 눈으로 잘 안 보입니다** — 조금 어긋나도
"확대가 좀 이상한데" 정도로 넘어가기 쉽고, 상자 좌표를 캐시하는 코드라 스크롤·레이아웃
변화에서 조용히 깨질 수 있습니다. 반드시 스크롤한 상태로 같이 확인하세요.
